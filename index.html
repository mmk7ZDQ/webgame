02三条路线

取决于你要的是「点开就玩」，还是「一个能看能下载的页面」。三者的工作量差了两个数量级。

云串流

可玩 100%
  • VPS 上跑 Android 容器（redroid / waydroid）+ 游戏本体
  • scrcpy 协议经 WebSocket 推到浏览器 canvas
  • 前端是纯静态页 → 直接挂 GitHub Pages
  • 延迟 30–80 ms，触控/多点手势可映射
工期 1–2 天 · 需一台 KVM VPS · 原版体验，零改动

TeaVM 移植

真·浏览器内
  • dex → class → TeaVM → WASM/JS，全套静态托管
  • 需自写 GL10/GL11 → WebGL1 固定管线兼容层
  • 需自写 android.* 桩：SurfaceView、Bitmap、Audio
  • 完成后是纯静态站，GitHub Pages 完整可玩
工期 2–2.5 人月 · 分两阶段可交付 · 体积 30–45 MB

静态分发页

不可玩
  • 介绍页 + 截图 + APK 下载 / Release 直链
  • 纯 HTML/CSS，零后端，零维护
  • 适合做入口页、更新日志、社区跳板

03架构分析

遍历全部 11,333 个方法体、54.6 万条指令后的还原结果。这一节推翻了初版预估里的两处判断。

// 分层图景（括号内为方法数）
appFramework      16 个 Activity（原生控件） + GameView 抽象基类
                    ├─ GameViewOpenGL     GLSurfaceView + EGL      (48)
                    ├─ GameViewThreaded   SurfaceView 独立线程      (33)
                    └─ GameViewNonSurface View.onDraw(Canvas)   (41) ★ 软件渲染路径
                          │
gameFramework/m    自研跨平台 2D 框架（~150 类）
                    ├─ m/h   唯一包装 android.graphics.Canvas 的类 (71)
                    └─ m/fm  GL 文本/精灵辅助（只 28 次 GL10）      (5)
                          │
gameFramework/b    3D / GPU 渲染层（~75 类）
                    └─ b/t   唯一直接调用 GLES20 的类（70 次）    (67)
结构事实 1
绘图有抽象层
m 包是自研框架，m/h 只是 Android Canvas 后端。换后端 = 改一个类，不动几千个调用点。
结构事实 2
GL 入口收敛
整个游戏只有 b/t 一个类碰 GLES20，WebGL 兼容层的边界非常干净。
结构事实 3
有软件后端
canvasDirectGL 开关 + Disabling opengl mode 日志 —— 关掉 GL 游戏仍可跑，只失去队伍着色与后处理。

修正一：桩的规模是 138 类 / 781 方法，不是 465 类。之前按"类型引用"数统计的 465 个类里， 有 327 个只在字段声明和异常签名里出现、从未被调用，写空壳即可。
修正二：可以把"能不能玩"和"画质如何"解耦。先实现 Canvas 软件路径（约 1–1.5 人月）拿到可玩版本， 再补 WebGL 层（约 1 人月）恢复全部特效。总工期从 2–4 人月下修到 2–2.5 人月，且中途有可交付点。
最大不确定性不在图形，在线程模型与千单位性能。GameViewThreaded 有独立渲染线程和 ReentrantLock 同步点遍布，Web 端必须改成单线程协作式让出；largeHeap=true 暗示后期单位上千。建议先做 1,000 单位最小压测再决定是否全额投入。

04移植蓝图（TeaVM 路线）

如果目标是「打开网页就能玩，且不养服务器」，这是唯一路径。核心工作量集中在四层替换。

层APK 中的实现Web 侧替代规模
图形javax.microedition.khronos GL10/GL11 + GLES20WebGL1 + 固定管线着色器模拟器71 个入口，~1.5k LOC
窗口GLSurfaceView / SurfaceHoldercanvas + requestAnimationFrame 主循环~400 LOC
输入MotionEvent / KeyEventPointerEvent / KeyboardEvent 映射~300 LOC
音频SoundPool / MediaPlayerWebAudio（decodeAudioData + 采样池）~350 LOC
存储java.io.File + SharedPreferencesOPFS / IndexedDB 挂载虚拟 FS~400 LOC
资源AssetManager 读 assets/预打包为 fetch + 虚拟路径表构建脚本
联网DatagramSocket 局域网WebRTC DataChannel 或降级为单机可选

构建链路的形状：

# 1. dex → class
d2j-dex2jar.sh txzz.apk -o rw.jar

# 2. 用桩实现替换 android.* / khronos.*（jar 前置于 classpath）
#    桩工程 → rw-web-stubs/build/libs/stubs.jar

# 3. AOT 编译到 WebAssembly
java -jar teavm-cli.jar -t wasm -d out/ \
     --main-class com.corrodinggames.rts.appFramework.MainActivity \
     -p rw.jar -p stubs.jar

# 4. 资源映射 + 静态托管
node tools/pack-assets.mjs assets/ out/assets/
# out/ 整体 push 到 gh-pages 分支即完成部署
关键判断：GLES 1.1 固定管线是这套方案能成立的原因。它只有 71 个入口、状态机简单、 没有可编程管线语义 —— 用一个统一着色器 + 顶点属性重排就能模拟。如果这个游戏用的是 自研 native 引擎 + Vulkan，这条路会直接封死。

05部署到 GitHub

本页已经是完整的静态站点，无构建步骤、无外部依赖，可直接作为仓库首页。

# 仓库初始化（在本目录执行）
git add -A
git commit -m "Rusted Warfare web deployment hub"
git branch -M main
git remote add origin git@github.com:<USER>/<REPO>.git
git push -u origin main

# 开启 Pages：Settings → Pages → Source: GitHub Actions
# workflow 已就绪：.github/workflows/pages.yml
给接手的 AI / 协作者：仓库根目录的 AGENTS.md 是完整交接记忆 —— 实测数据、架构速查表、需改的类清单、当前状态、下一步选项、环境坑、以及 5 条未验证假设。 任何新会话读完它就能接着干，不必重新分析 APK。
体积提醒：GitHub Pages 单文件上限 100 MB、站点建议 1 GB 内。21.7 MB 的 assets/ 完全放得下，但 25 MB 的 APK 本体建议走 Release 附件而不是提交进仓库 —— 既避开大文件存储限制，也让 git clone 保持轻量。
